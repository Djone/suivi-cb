README intégré

Mode opératoire d'une montée de version

À suivre dans l'ordre
  1. Finaliser et pousser la branche de développement.
  2. dry-run pour contrôler Git et exécuter les tests.
  3. prepare pour clôturer la version et créer le commit.
  4. Construire et tester Docker sur le poste local.
  5. deploy pour fusionner, pousser et créer le tag.
  6. Créer la branche suivante, puis mettre à jour le NAS plus tard.
Afficher le guide complet

1. Avant de commencer

  • La branche à livrer doit contenir tous les commits et être poussée.
  • git status doit indiquer un répertoire propre.
  • Les tickets livrés doivent être done et cibler la version stable.
  • Aucun secret, fichier .env ou fichier de base ne doit être commité.

2. Réglages recommandés

Version stableEx. 1.6.0
Prochaine version devEx. 1.7.0-dev
Branche ciblemaster
  • Les options commit et rollback-on-failure sont présélectionnées : les conserver activées.
  • Laisser create-release-branch décoché si la branche dev existe déjà.
  • Laisser toutes les options avancées désactivées pour une release normale.

Lancer dry-run, contrôler le rapport, puis lancer prepare. Cette seconde action archive les notes de version, met à jour les numéros et crée le commit de préparation.

3. Validation Docker locale

Démarrer Docker Desktop puis, depuis la racine du projet :

scripts\build-production.bat
docker compose up -d
docker compose ps
docker compose logs --tail=100

Ouvrir http://localhost:4200, vérifier la version, les pages modifiées et l'état des conteneurs. Le script de build ne démarre pas les conteneurs à lui seul. Après validation : 

docker compose down

4. Publication Git

Lancer deploy et confirmer l'exécution réelle. L'assistant actualise master, fusionne la branche courante, pousse master et crée le tag stable. Il n'installe rien sur le NAS.

La commande technique full n'est volontairement pas affichée : elle ne laisse pas d'étape de validation Docker entre prepare et deploy.

5. Développement suivant

Après la publication Git, repartir du master actualisé : 

git switch master
git pull --ff-only origin master
git switch -c <prochaine-version>-dev
git push -u origin <prochaine-version>-dev

6. Mise à jour du NAS, immédiate ou différée

La release doit d'abord exister sur origin/master.

cd /volume1/docker/suivi-cb
git status --short --branch
GIT_BRANCH=master ./scripts/update.sh
sudo docker-compose ps
sudo docker-compose logs --tail=100

update.sh sauvegarde la base, récupère master, reconstruit les images, redémarre les conteneurs et teste l'API. En cas d'échec, il restaure le code et la base précédents.

La version documentaire de ce guide est conservée dans frontend/src/app/components/release-process/README.md.

Repères sur les actions

Vérifier et préparer

  • dry-run contrôle Git et les tests sans rien modifier.
  • prepare met à jour les versions et les notes, puis crée le commit si l'option recommandée est active.

Publier

  • deploy effectue toujours la publication réelle après confirmation : fusion dans master, push et tag.
  • Il ne déploie pas sur le NAS : cette opération reste assurée par update.sh.

Options avancées

  • Elles servent uniquement à un dépannage ou à un workflow Git particulier.
  • Chaque option possède une explication visible et une infobulle au survol.
  • Les laisser désactivées dans le parcours normal.
