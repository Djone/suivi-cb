Clôture de version

Assistant de release

Automatise les contrôles et la publication Git. La validation en préproduction et la MEP restent des étapes NAS à confirmer séparément.

README intégré

Parcours obligatoire : Dev → préproduction → MEP

Ne pas sauter d'étape
  1. Dev : terminer les changements et valider les tests fonctionnels.
  2. Contrôles dev : lancer dry-run, puis prepare pour créer le commit candidat.
  3. Préparer la candidate : pousser le commit préparé, construire et transférer les images vers la préproduction.
  4. Préproduction : déployer et tester la candidate ; noter le commit et les identifiants des deux images validées.
  5. Publication Git : après validation préprod, lancer deploy pour fusionner et créer le tag.
  6. MEP : promouvoir les mêmes images sur la production, sans reconstruire.
Afficher le guide complet

1. Développement et validation locale

  • Terminer les changements sur la branche de développement et vérifier les fonctionnalités concernées sur l'application locale.
  • Exécuter dry-run depuis cette page : il vérifie l'état Git et lance les tests automatisés.
  • Les tickets livrés doivent être done et cibler la version stable.
  • Aucun secret, fichier .env ou fichier de base ne doit être commité.

2. Préparer le commit candidat

Version stableEx. 1.6.0
Prochaine version devEx. 1.7.0-dev
Branche ciblemaster
  • Les options commit et rollback-on-failure sont présélectionnées : les conserver activées.
  • Laisser create-release-branch décoché si la branche dev existe déjà.
  • Laisser toutes les options avancées désactivées pour une release normale.

Après un dry-run réussi, lancer prepare. Cette action relance les contrôles, archive les notes, met à jour les versions et crée le commit candidat si l'option correspondante est activée. Vérifier le rapport et l'état Git.

prepare ne pousse pas le commit. Pousser explicitement la branche candidate avant de la rendre disponible pour la construction préproduction. Ne pas modifier ensuite le code ou la configuration de l'image : toute modification impose une nouvelle candidate et une nouvelle validation.

3. Construire et installer la candidate en préproduction

Utiliser la commande du panneau « Package de préproduction » pour construire, exporter et transférer les images du commit candidat. Suivre ensuite la checklist de candidate préproduction du dépôt pour la plateforme Docker du NAS, l'import, la configuration isolée et le démarrage. Ne pas utiliser le Compose de production.

La commande s'exécute dans le terminal du PC pour permettre la saisie du mot de passe SSH. Elle vérifie le transfert et s'arrête avant l'installation sur le NAS. Le mode opératoire est dans docs/AUTOMATISATION_CANDIDATE.md.

4. Tester et approuver la préproduction

Exécuter les contrôles fonctionnels et techniques définis pour la candidate. Consigner le commit, la date de validation, les identifiants exacts des images backend et frontend et les résultats. Les tags seuls ne suffisent pas : ils peuvent être déplacés.

En cas d'échec, ne pas lancer deploy. Corriger sur la branche de développement, puis reprendre le parcours avec une nouvelle candidate.

5. Publier la release dans Git

Seulement après l'approbation préprod, lancer deploy depuis la branche candidate et confirmer l'exécution réelle. L'assistant relance les tests, fusionne la branche dans master, pousse le tag stable et peut créer la branche du cycle suivant. Cette action publie dans Git ; elle ne déploie rien sur le NAS.

La commande full n'est pas adaptée : elle enchaîne préparation et publication sans laisser le temps de valider la candidate en préproduction.

6. Effectuer la MEP

Après sauvegardes et vérifications de production, promouvoir les images identiques à celles testées en préproduction, en conservant la configuration et les données de production. Ne pas reconstruire depuis Git ou sur le NAS de production. Suivre docs/PROMOTION_PREPROD_PRODUCTION.md.

scripts/update.sh fait un git pull et reconstruit les images : il ne doit pas être utilisé pour cette MEP.

La version documentaire de ce guide est conservée dans frontend/src/app/components/release-process/README.md.

Repères sur les actions

Vérifier et préparer

  • dry-run contrôle Git et les tests sans rien modifier.
  • prepare met à jour les versions et les notes, puis crée le commit si l'option recommandée est active.

Préproduction puis publication

  • La validation préproduction et la MEP sont des opérations manuelles sur le NAS ; consigner le commit et les identifiants des images approuvées.
  • deploy ne doit être lancé qu'après le feu vert préproduction. Il fusionne dans master, pousse le tag, mais ne déploie pas sur le NAS.
  • La production reçoit les images préproduction existantes ; update.sh et toute reconstruction sont exclus de la MEP.

Options avancées

  • Elles servent uniquement à un dépannage ou à un workflow Git particulier.
  • Chaque option possède une explication visible et une infobulle au survol.
  • Les laisser désactivées dans le parcours normal.
