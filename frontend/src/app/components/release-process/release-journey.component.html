Du PC au NAS

Créer, tester et livrer la candidate

Suivez ces étapes dans l'ordre. Les actions automatiques se font ici ; les commandes NAS sont à copier dans votre session SSH.

Une installation initiale, puis un parcours répétable

Les cinq lots construisent le dispositif de livraison. Il ne faut pas les redévelopper à chaque version : les tests, le pipeline et ce dossier sont ensuite réutilisés. Les résultats doivent toutefois concerner la candidate effectivement livrée.

Comprendre les contrôles et les actions encore nécessaires

À mettre en place une fois, puis maintenir

  • Pipeline de tests et scans, distribution des images, dossier de preuves et moteur de livraison.
  • Canal de déploiement NAS contrôlé, accès minimaux et approbations GitHub. Aucun code de PR non fiable ne doit accéder au NAS ou aux secrets de livraison.
  • GHCR est le registre retenu pour l'automatisation. Un autre registre ou un transfert TAR/SSH vérifié peut assurer la distribution ; GHCR n'est pas une obligation technique universelle. Un exécuteur permanent sur le NAS n'est pas obligatoire non plus : c'est le canal contrôlé qui l'est.

À chaque candidate livrée

  1. Git et CI : commit propre, poussé et relu ; tests métier/sécurité, audits de dépendances et scans réussis ; exceptions justifiées et non expirées.
  2. Distribution : construire une fois ; conserver les images par version et digest, manifeste, SBOM et preuves. Le parcours GHCR prévu reste à activer ; le ZIP/TAR vérifié sert de secours.
  3. Préproduction : déployer les images exactes sans reconstruction via le canal NAS contrôlé ; vérifier import, architecture et identité. Les scripts actuels sont lancés explicitement par l'opérateur ; ce n'est pas encore un déploiement GitHub entièrement automatique.
  4. Recette finale : utiliser ce dossier avec la candidate finale, joindre les résultats NAS et les contrôles concernés du lot de livraison. Une correction produit une nouvelle candidate et impose de refaire les validations concernées.
  5. Dossier cohérent : tests, pipeline et preuves liés au même commit et aux mêmes images ; aucun blocage non résolu, réserves explicitement acceptées et à jour.
  6. Approbation humaine : confirmer la candidate, les digests, le plan de livraison, la sauvegarde et le retour aux anciennes images compatibles. Prévoir le cycle de version suivant. L'approbation n'est jamais déduite d'une CI verte.
  7. Publication et promotion : tag et release du commit retenu selon le parcours approuvé ; sauvegarde cohérente juste avant la bascule, puis mêmes images en production. Le moteur et le rollback doivent d'abord être qualifiés en environnement isolé. Aucun retour aux anciennes images ne restaure automatiquement les données.
  8. Après MEP : santé, version, accès, parcours critiques et sauvegarde ; archiver le rapport et vérifier l'ouverture du cycle suivant.

À reprendre selon les changements ou périodiquement

L'audit complet de sécurisation initial n'est pas à refaire intégralement pour chaque correction. Refaire l'analyse des zones modifiées, notamment authentification, permissions, migrations, dépendances et infrastructure. Réexaminer les droits et exercices de restauration selon leur calendrier ou après modification ; conserver leur date et leur périmètre. Une preuve ancienne ne valide pas automatiquement une configuration qui a changé.

La courte recette humaine NAS concerne le proxy, OTP, les accès et les parcours touchés. Les suites automatisées couvrent les régressions répétitives. Tout report de la rétention et de l'alerte USB reste une réserve documentée, pas un test réussi.
