3. Préparer le NAS de préproduction

D'abord sur le PC, puis dans File Station et la session SSH NAS

Créez d'abord la candidate à l'étape 2.

  1. Dans le dossier de preuves, renseigner le périmètre et les notes, les figer puis confirmer leur revue. Aucun test NAS n'est encore à cocher.
  2. Télécharger le package et le kit de préproduction.

    Le kit contient les scripts revus, les empreintes et la configuration du realm de test. Sa génération ne modifie pas le NAS.

  3. Dans votre terminal SSH habituel, vérifier les ressources et les services actuels : 
    {{inspectNas}}

    Au moins 512 Mo disponibles avant le déploiement. Ne jamais arrêter les conteneurs de production ou Keycloak pour libérer de la mémoire. Si une ancienne recette doit être arrêtée, vérifier son nom avec le mainteneur.

  4. Créer le dossier de transfert. L'UID 1028 correspond ici à GodOfNasAugerie ; ne pas reprendre cette commande sur un autre NAS sans vérifier son compte. 
    {{createNasDirectory}}
  5. Dans File Station, ouvrir {{ remote }}. Y envoyer les deux fichiers téléchargés. Extraire le ZIP dans candidate-{{ runId }}, et le kit TAR dans ce même dossier de release. Il doit y avoir deux sous-dossiers voisins : candidate-{{ runId }} et nas-kit.
  6. Dans le terminal SSH NAS, préparer et vérifier le plan : 
    {{nasPreparation}}

    Toutes les empreintes affichent OK, puis PLAN_ONLY et NAS_PREPARATION_PLAN_OK. Aucun service applicatif n'est remplacé. En cas d'erreur, s'arrêter ici.

  7. Après ce résultat, démarrer explicitement la préproduction isolée :

    Cette commande utilise les images importées, sans rebuild. Elle ne touche ni aux données de production ni à Keycloak.

Vérifier le bon site

Dans DSM, le reverse proxy de finances-preprod.jolurie.com doit viser 127.0.0.1:4205 pour cette nouvelle pile. L'ancienne RC8 utilisait le port 4201. Vérifier le pied de page : la version attendue est {{ candidate || "celle du dossier" }}. Ne pas continuer si vous voyez une ancienne version.

Connexion et droits

  1. Se connecter avec un compte autorisé du realm suivi-cb-preprod. Les comptes/opérations doivent se charger, API 200.
  2. Tester OTP, déconnexion puis rechargement d'une page protégée : nouvelle connexion demandée.
  3. Attendre plus de cinq minutes en utilisant le site. Dans F12 → Réseau, confirmer une requête token avec grant_type=refresh_token et HTTP 200, puis une API métier 200. Vérifier que l'audience contient suivi-cb-api et le realm reste suivi-cb-preprod. Ne pas copier les jetons dans le rapport.
  4. Utiliser un compte sans rôle app-user : écran Accès non autorisé, aucun chargement métier et déconnexion accessible. Pour confirmer le refus API, exécuter ce JavaScript dans F12 → Console du navigateur, jamais dans PowerShell ou SSH avec le jeton de ce compte :

    Statut API : 403.

6. Préparer la production puis effectuer la MEP supervisée

La publication et la MEP sont actuellement verrouillées à votre demande. Cette page ne lance aucune commande en production. Les conditions d'approbation et le moteur de promotion du lot 2 doivent être terminés avant d'activer cette étape.

  1. Planifier la fenêtre de livraison et faire approuver explicitement la candidate, ses images et le retour arrière. Ne pas reconstruire après la recette NAS.
  2. Conserver les anciennes images et leur configuration. Relever les conteneurs actuels en lecture seule : 
    {{inspectProduction}}
  3. Avant la bascule approuvée, lancer la chaîne de sauvegarde cohérente : 
    {{backup}}
    {{nasBackupCheck}}

    Un nouveau run-... doit avoir status.txt=SUCCESS et sha256sum -c SHA256SUMS sans erreur. Le retrouver dans published et prévoir sa copie USB ; un ancien succès ne prouve pas la sauvegarde de cette MEP. Attendu : BACKUP_AND_PUBLICATION_OK. Dans Hyper Backup, lancer si nécessaire Sauvegarder maintenant, puis retrouver le même run dans l’explorateur USB.

  4. Préparer et relire docker-compose.production.yml avec les images testées, pull_policy: never, les volumes de production existants et .env.production avec realm suivi-cb. Ne pas copier la base ou les comptes de recette. Valider sa syntaxe : 
    {{productionPlanCheck}}

    La première bascule depuis des conteneurs individuels exige un plan validé de reprise des noms, volumes, réseaux et du proxy. Ne pas supprimer ces ressources pour contourner un conflit.

  5. Après déblocage et approbation, promouvoir uniquement backend et frontend avec les images exactes, sans rebuild ni redémarrage de Keycloak. Le lancement de cette bascule n'est pas activé ici.
  6. Vérifier sur finances.jolurie.com : HTTPS, version attendue, realm suivi-cb, API 401 sans jeton, 403 sans rôle, connexion, OTP, refresh, déconnexion, lecture des comptes/opérations et journaux.
  7. En cas d'échec, appliquer le plan de retour aux anciennes images compatibles en conservant la base courante et les nouvelles écritures. Aucune restauration automatique de base. Toute restauration de données exige une décision distincte.

  1. Confirmer les contrôles après MEP et la sauvegarde.

  3. Exporter et archiver le rapport du dossier de preuves, conserver le manifeste, les SBOM, les images et le plan de rollback.
  4. Clôturer seulement lorsque le dossier ne contient plus de blocage. Une case de l'ancien assistant ne suffit pas.
